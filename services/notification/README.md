# notification-service

Tells customers what happened to their orders. It reacts to the order outcome events and sends an email, and for cancellations also an SMS. Delivery goes through a `Sender` port; this repository ships a **simulated** sender that writes a log line, so the whole flow can be demonstrated without an email or SMS provider.

## Interfaces

| Kind | Name | Description |
|---|---|---|
| Event (consumed) | `order.evt.confirmed` | Sends one email: order confirmed, with the total |
| Event (consumed) | `order.evt.cancelled` | Sends an email and an SMS explaining why the order was cancelled |
| gRPC | `NotificationService.ListNotifications` | What was sent, newest first; filter by order and/or customer; opaque page tokens |

Payment declines need no separate subscription: the order service always follows them with `order.evt.cancelled`, whose reason ("payment failed: ...") becomes the explanation.

Contracts: [`api/proto/ecommerce/notification/v1`](../../api/proto/ecommerce/notification/v1). Subjects: [`pkg/subjects`](../../pkg/subjects/subjects.go).

## Behaviour worth knowing

- **Never notifies twice for a repeated event.** A notification is recorded under a unique `(order, kind, channel)` before it is sent, so a redelivered or duplicated event finds what was already done. Sent notifications are not sent again.
- **Channels are independent.** If the SMS gateway fails, the email still goes out. The event is redelivered and only the notification that is still pending is retried.
- **Undeliverable is a result, not an error.** A permanently undeliverable message (unknown mailbox, unreachable number) is recorded as `FAILED` with the reason and is never retried.
- **A notification problem never affects an order.** This service only reads order events and has no way to change an order.
- **Delivery is at-least-once.** If the process dies after a message was sent but before it was marked sent, or two instances handle the same event at the same moment, a message can be sent more than once. It is never lost. See [ADR-0014](../../docs/adr/0014-notification-delivery-guarantees.md).
- **Malformed events** (garbage, or missing order or customer) are terminated instead of blocking the queue.

## Known limitation: recipients

Events carry a `customer_id` but no contact details, so **the customer ID is used as the address** for both email and SMS. A real system would look the contact up (a customer service, or a table kept here). The sender is behind a port, so this change would not touch the rest of the service.

## Simulated sender

Choose the behaviour with the customer ID:

| Customer ID | Result |
|---|---|
| starts with `bounce-` | permanently undeliverable (`mailbox does not exist` / `number not reachable`) |
| starts with `flaky-` | the first attempt of each notification fails with a gateway timeout, then succeeds |
| anything else | delivered (logged) |

## Layout

```
cmd/notification/                   wiring only
internal/domain/                    Notification, message templates, cancellation explanations
internal/app/                       NotifyOrderConfirmed / NotifyOrderCancelled / ListNotifications + ports (Repository, Sender)
internal/adapters/grpc/             gRPC server and page tokens
internal/adapters/nats/             order event handlers
internal/adapters/postgres/         repository; sqlcgen/ is generated by sqlc
internal/adapters/sender/simulated/ fake email/SMS sender
internal/integration/               end-to-end tests (Postgres + NATS)
migrations/                         goose SQL migrations (embedded in the binary)
```

## Configuration (environment)

| Variable | Default | Description |
|---|---|---|
| `DATABASE_URL` | *required* | PostgreSQL connection string |
| `NATS_URL` | `nats://localhost:4222` | NATS server |
| `GRPC_ADDR` / `HTTP_ADDR` | `:9090` / `:8080` | gRPC and `/healthz` `/readyz` |
| `SHUTDOWN_TIMEOUT` | `15s` | Graceful shutdown limit |
| `LOG_LEVEL` / `LOG_FORMAT` | `info` / `json` | `debug\|info\|warn\|error`, `json\|text` |

## Try it

```bash
make up                                  # whole stack; notification gRPC on :9093, health on :8084
grpcurl -plaintext -d '{"customer_id":"alice"}' localhost:9093 ecommerce.notification.v1.NotificationService/ListNotifications
docker compose -f deploy/docker-compose.yml logs notification   # the simulated deliveries
```

## Test it

```bash
go test -short ./services/notification/...   # unit tests, no Docker
go test ./services/notification/...          # plus integration tests (Docker required)
make e2e                                     # all services together, black box
```
