# payment-service

Charges customers for orders through a payment provider and tells the order-service whether it worked. The provider is a port: this repository ships a **simulated** provider so every outcome of the saga can be demonstrated without a real processor.

## Interfaces

| Kind | Name | Description |
|---|---|---|
| gRPC | `PaymentService.GetPayment` | The payment recorded for an order (`NOT_FOUND` if none) |
| Command | `payment.cmd.charge` (`ChargePayment`) | Charge the customer for an order |
| Event | `payment.evt.succeeded` (`PaymentSucceeded`) | Charge succeeded; carries the payment ID |
| Event | `payment.evt.failed` (`PaymentFailed`) | Charge declined; carries the reason |

Contracts: [`api/proto/ecommerce/payment/v1`](../../api/proto/ecommerce/payment/v1). Subjects: [`pkg/subjects`](../../pkg/subjects/subjects.go).

## Behaviour worth knowing

- **Never charges an order twice.** There is at most one payment per order (`UNIQUE order_id`). A repeated command re-publishes the stored outcome and does not call the provider again. A repeat for the same order with a different amount or customer is rejected as invalid and the original stands.
- **A decline is a result, not an error.** It is recorded, reported with `PaymentFailed`, and never retried. A provider *outage* is the opposite: nothing is stored and the command is redelivered.
- **The provider is called outside any database transaction**, so a slow provider cannot hold a connection. If the process dies between the charge and the write, the retry reaches the provider again, which returns the same result for the same order (idempotency key). See [ADR-0012](../../docs/adr/0012-payment-provider-outside-transaction.md).
- **Concurrent attempts agree.** If two workers race, the first stored payment wins and both publish its outcome.
- **Replies are transactional.** The payment row and its outcome event are written to the outbox in one transaction.
- **Malformed commands** are terminated, not retried.

## Simulated provider

Choose the outcome with the customer ID or amount:

| Input | Result |
|---|---|
| customer starts with `decline-` | declined: `card declined` |
| amount above `SIMULATED_MAX_AMOUNT_MINOR` (default `1000000`) | declined: `amount exceeds limit` |
| customer starts with `flaky-` | the first attempt per order fails as an outage, then succeeds |
| anything else | succeeds |

## Layout

```
cmd/payment/                       wiring only
internal/domain/                   Payment, ChargeRequest validation, DeclinedError
internal/app/                      Charge / GetPayment + ports (Provider, Repository, Transactor, Events)
internal/adapters/grpc/            gRPC server
internal/adapters/nats/            command handler and event publisher (outbox)
internal/adapters/postgres/        repository; sqlcgen/ is generated by sqlc
internal/adapters/provider/simulated/   fake provider
internal/integration/              end-to-end tests (Postgres + NATS)
migrations/                        goose SQL migrations (embedded in the binary)
```

## Configuration (environment)

| Variable | Default | Description |
|---|---|---|
| `DATABASE_URL` | *required* | PostgreSQL connection string |
| `NATS_URL` | `nats://localhost:4222` | NATS server |
| `GRPC_ADDR` | `:9090` | gRPC listen address |
| `HTTP_ADDR` | `:8080` | `/healthz` and `/readyz` |
| `SIMULATED_MAX_AMOUNT_MINOR` | `1000000` | Largest amount the simulated provider accepts |
| `SHUTDOWN_TIMEOUT` | `15s` | Graceful shutdown limit |
| `LOG_LEVEL` / `LOG_FORMAT` | `info` / `json` | `debug\|info\|warn\|error`, `json\|text` |

## Run and test

```bash
make up                                  # NATS, Postgres, inventory and payment (gRPC on :9091, health on :8082)
curl localhost:8082/readyz
go test -short ./services/payment/...    # unit tests, no Docker
go test ./services/payment/...           # plus integration tests (Docker required)
```
