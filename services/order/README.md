# order-service

Takes orders and runs the **order saga**: it asks inventory to reserve stock, asks payment to charge the customer, and then confirms the order, or rolls everything back. It is the only service that knows the whole workflow ([ADR-0004](../../docs/adr/0004-orchestrated-saga.md)).

## The saga

```
CreateOrder ──► PENDING ──ReserveStock──► inventory
                  │ StockReserved               │ StockRejected
                  ▼                             ▼
            STOCK_RESERVED ──ChargePayment──►   CANCELLED  (nothing reserved: nothing to undo)
                  │ PaymentSucceeded │ PaymentFailed
                  ▼                  ▼
              CONFIRMED          CANCELLED  ◄── ReleaseStock sent (compensation)
```

Customer cancellation and the timeout sweeper also lead to `CANCELLED`, always with a `ReleaseStock`. `CONFIRMED` is final.

## Interfaces

| Kind | Name | Description |
|---|---|---|
| gRPC | `OrderService.CreateOrder` | Accepts an order as `PENDING`; idempotent per `(customer_id, idempotency_key)` |
| gRPC | `OrderService.GetOrder` / `ListOrders` | One order, or a newest-first page (opaque token, optional customer filter) |
| gRPC | `OrderService.CancelOrder` | Cancel before confirmation; `FAILED_PRECONDITION` once confirmed |
| gRPC client | inventory `GetStock` | Authoritative unit prices, fetched in parallel with per-call deadlines |
| Command | `inventory.cmd.reserve` / `inventory.cmd.release` | Reserve stock for the order / give it back |
| Command | `payment.cmd.charge` | Charge the customer for the order total |
| Reply (consumed) | `inventory.evt.reserved` / `rejected`, `payment.evt.succeeded` / `failed` | Drive the state machine |
| Event | `order.evt.confirmed` / `order.evt.cancelled` | Outcome, for notifications and anyone else |

## Behaviour worth knowing

- **Prices come from the catalogue, never from the client.** A price in the request is ignored; the order is priced from inventory. The total is computed with overflow checks.
- **Idempotent creation.** A repeated request returns the original order and starts nothing new, even under concurrent identical requests. Reusing a key for a *different* request is `ALREADY_EXISTS`.
- **Every state change is one transaction:** order row, outbox message (the next command or the outcome event) and inbox record commit together, so a crash can neither lose a step nor apply it twice.
- **Replies are idempotent.** Duplicates and out-of-order replies are ignored by the state machine, on top of the inbox.
- **Compensation.** Payment declined, customer cancels, or timeout: the order is cancelled and stock is released. A reservation that arrives *after* a cancellation is released again, so stock is never stranded.
- **Saga timeout.** A sweeper cancels orders that have waited longer than `SAGA_TIMEOUT` for a reply (a lost reply must not leave an order stuck forever).
- **Known limitation: refunds.** A customer cannot cancel a confirmed order (that needs a refund flow). If a payment succeeds for an order that was already cancelled or timed out, the order is flagged `refund_required` and an error is logged; actually refunding is future work. See [ADR-0013](../../docs/adr/0013-saga-failure-handling.md).
- **Correlation.** The order ID is the correlation ID carried on every command and event of its saga, so one order can be followed across all services.

## Layout

```
cmd/order/                         wiring only
internal/domain/                   Order, state machine, pricing and validation
internal/app/                      use cases and saga steps + ports (Catalog, Repository, Transactor, Commands, Events)
internal/adapters/grpc/            gRPC server, error mapping, page tokens
internal/adapters/nats/            reply handlers (inbox) and command/event publisher (outbox)
internal/adapters/inventory/       gRPC client used for pricing
internal/adapters/postgres/        repository; sqlcgen/ is generated by sqlc
internal/integration/              saga tests (Postgres + NATS, scripted participants)
migrations/                        goose SQL migrations (embedded in the binary)
```

## Configuration (environment)

| Variable | Default | Description |
|---|---|---|
| `DATABASE_URL` | *required* | PostgreSQL connection string |
| `NATS_URL` | `nats://localhost:4222` | NATS server |
| `INVENTORY_GRPC_ADDR` | `localhost:9090` | inventory-service gRPC address (pricing) |
| `INVENTORY_TIMEOUT` | `3s` | Deadline for each price lookup |
| `SAGA_TIMEOUT` | `2m` | How long an order may wait for a reply before being cancelled |
| `SWEEP_INTERVAL` | `10s` | How often the timeout sweeper runs |
| `GRPC_ADDR` / `HTTP_ADDR` | `:9090` / `:8080` | gRPC and `/healthz` `/readyz` |
| `SHUTDOWN_TIMEOUT` | `15s` | Graceful shutdown limit |
| `OTEL_EXPORTER_OTLP_ENDPOINT` | | OTLP/gRPC endpoint for traces (e.g. `http://jaeger:4317`); unset disables export. `/metrics` is served on `HTTP_ADDR` |
| `LOG_LEVEL` / `LOG_FORMAT` | `info` / `json` | `debug\|info\|warn\|error`, `json\|text` |

## Try it

```bash
make up                                  # whole stack; order gRPC on :9092, health on :8083
grpcurl -plaintext -d '{"customer_id":"alice","idempotency_key":"k1","items":[{"sku":"MUG-GOPHER-001","quantity":2}]}' \
  localhost:9092 ecommerce.order.v1.OrderService/CreateOrder
# customer ids starting with "decline-" are declined by the simulated payment provider
```

## Test it

```bash
go test -short ./services/order/...      # unit tests, no Docker
go test ./services/order/...             # plus saga integration tests (Docker required)
make e2e                                 # all services together, black box
```
